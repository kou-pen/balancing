## 実務上の重要な補足

### 完了条件と自動クローズ
- 複数PRのうち一部しか解決しないPRに `Closes #N` を書かない。代わりに `Refs #N`。
- 受入条件すべてが満たされた場合のみ最終PRで `Closes #N` を使用できる。
- 安全・実機検証Issueは自動で閉じるキーワードを使わず、ユーザーの確認を受ける。
- AIが問題を見つけたらIssueを検索して重複を避ける。Issueの削除は禁止。

### 検証とレビュー
- `PASS` は実行した試験のみ。`NOT RUN` と推定結果は明示。
- 実機検証が未完でも実装PRをマージできるが、必ず未検証事項を別Issueで追跡する。
- Blockerは安全・重大仕様違反、Majorは重大機能・設計問題、Minorは軽微、Suggestionは任意。
- 安全仕様の変更や実機駆動を伴う作業は事前承認を必要とする。

### 検証記録・ADRの最低項目
- ADR: 背景、選択肢、決定、根拠、影響、関連Issue/PR。
- 検証: 使用コミット、実行環境、設定値、手順、実測値、合否、未検証事項。
- 未実施・仮定・推測は実測と明確に区別する。

### Issue管理と作業引き継ぎ
- issueコメント/PRに、現状、試験、ブロッカー、次のコマンド、作業ブランチ、コミットIDを残す。
- ローカル補助記録はGit追跡対象と分離。秘密鍵や認証情報を書かない。
- 週1回の棚卸しは運用頻度の決定であり、**定期実行そのものを有効にしたことを意味しない**。
