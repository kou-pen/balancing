# F446 CANイベント回収・配送の検証

[共通CANポート](f446-can1-rs06-port-host.md) のイベントをメインループで回収し、CAN1/CAN2を識別したまま配送します。契約は [BOARD-F446-001](../specs/boards/f446_control.md) と [公開API設計](../design/public-api.md) を参照してください。

<pre class="mermaid">
sequenceDiagram
    participant I as CAN IRQ
    participant P as CanPort
    participant A as 主ループ
    participant R as CanRouter
    participant S as 受け取り側
    I->>P: captureInterrupt
    loop 交互に1件、各バス最大19件
        A->>P: pollCanEvents から popEvent
        P-->>A: 採取済みイベント
        A->>R: 発生元のバスとイベントを渡す
        R->>S: 受信・TX終端・ポート状態を通知
    end
</pre>

F446の現在の起動経路では `balancing_f446_can1_service()` がCAN1だけを渡し、500 Hzのメイン処理で [既存のCAN1監視結果](f446-can1-runtime-host.md) を更新します。CAN2はホスト試験で同じ回収処理に接続します。

## 回収順と境界

- 一度の呼び出しでCAN1、CAN2の順に各1件を試みます。各ポート最大19件で、両ポートが満杯のときは最大38件です。空を観測したポートにその後届いたイベントは次回回収します。
- `CanPort` が先に返すbus-off・復旧・受信欠落をその順で配送します。異なるバス間やイベント種別間の時刻順ソートは行わず、採取時刻を保持します。
- `CanRouter` は受信、ハードウェアで確定した送信終端、ポート状態を別々のコールバックへ渡します。同じ値の送信トークンも発生元のバスが異なれば別の終端です。コールバックはポートのIRQマスク区間を抜けた後に実行します。

## 機器別の受信振り分け

| 発生元 | CAN ID | DLC | 配送先 |
| --- | --- | --- | --- |
| CAN1 | 拡張29 bit、上位5 bitがType 2または24 | 8 | RS06状態報告 |
| CAN2 | 標準 `0x201` | 8 | C620左車輪フィードバック |
| CAN2 | 標準 `0x202` | 8 | C620右車輪フィードバック |
| その他 | バス・ID形式・ID・DLCのいずれかが不一致 | 任意 | 未分類 |

詳細は [RS06](../specs/protocols/rs06_can1.md) と [C620](../specs/protocols/c620_can2.md) の仕様を参照してください。RS06の主機ID・軸IDとペイロードの検証はCodec／機器サービスで行います。未確定のF303・PiフレームとCAN2の電流指令 `0x200` は未分類で、診断側は元フレームと採取時刻を引き続き受け取れます。既存のCAN1監視カウンタは全受信イベントの集計です。

## バスごとの送信終端の照合

`CanTxScheduler::trySubmit(frame, token, nowUs)` は1バスの `CanPort` に投入し、`Accepted` のときにトークンと受付時刻を記録します。最大3件まで記録し、`Busy` の要求は呼出側で扱います。終端していない番号の再投入は `Busy` です。終端した番号の再利用を避ける責任は送信要求元にあります。

<pre class="mermaid">
sequenceDiagram
    participant S as 送信要求元
    participant T as CanTxScheduler
    participant P as CanPort
    participant R as CanRouter
    S->>T: trySubmit
    T->>P: trySend
    P-->>T: Accepted
    T-->>S: 受付結果
    Note over P,R: IRQで終端を記録し、主ループで回収
    P-->>R: 発生元バスと終端イベント
    R->>T: 発生元バスだけ照合
    T-->>R: 受付済みの枠を解放
    R-->>S: onCanTransmit
</pre>

完了の時刻にはIRQ採取時刻を使います。受付時刻と同時刻は有効で、受付より前の時刻、未受付のトークン、配送済みの重複を棄却します。送信成功、仲裁負け、送信エラー、中止を含む未送信のいずれも終端として配送し、上位側が結果に応じて処理します。受信イベントから送信完了を補いません。

`CanRouter` の照合先はポートごとに設定し、従来のポート単体試験のように照合先が未設定の場合はポートの終端を直接配送します。F446の起動経路ではCAN1のスケジューラを接続しました。CAN1監視には送信要求元がなく、CAN2との組み合わせはホストで確認しました。

## 周期送信の最新値と期限

`replacePeriodic(batch, nowUs)` はバスごとに、世代番号・絶対期限・対象別の送信候補を一括で更新します。未指定の対象も旧世代から消えます。RS06の4軸は最大4件、C620の左右指令は共通フレーム1件です。上位が期限と世代を発行します。

<pre class="mermaid">
flowchart TD
    A["CAN終端を回収"] --> B["新しい周期があれば待ち候補を置換"]
    B --> C{"待ち候補の期限内か"}
    C -->|期限切れ| D["破棄したトークンを返す"]
    C -->|期限内| E{"旧周期がすべて終端済みか"}
    E -->|未終端| F["送信待ちを保持"]
    E -->|終端済み| G["空きメールボックスに1件投入"]
</pre>

`service(nowUs)` は周期フレームを対象キー順に1件ずつ処理し、`Accepted` と `Expired` で対応するトークンを返します。周期フレームだけなら1バスあたり最大4回で1世代の候補を確認できます。HAL受付済みの旧フレームは終端まで保持し、終端結果を元のトークンで配送します。同じ世代なら、3件のうち1件が終われば4件目を投入できます。期限ちょうどから期限切れです。正当な新世代が到着時点で期限切れなら、旧世代の待ちも破棄します。無効な一括入力では従前の世代を保持します。

## 通常イベントFIFO

通常イベントの発行側は絶対送信期限とトークンを付けて `enqueueEvent(request, nowUs)` へ渡します。FIFOの固定領域はバスごとに呼出側が用意します。満杯なら `QueueFull` を返し、待っているフレームと順序を保持します。登録時点で期限切れなら `Expired` を返します。登録後に期限に達した先頭フレームは `service(nowUs)` が破棄し、トークン付きで通知します。

<pre class="mermaid">
flowchart TD
    A["CAN終端を回収"] --> B{"通常イベントの待ちがあるか"}
    B -->|ある| C{"先頭は期限内か"}
    C -->|期限切れ| D["破棄してトークンを返す"]
    C -->|期限内| E{"通常イベントが受付済みか"}
    E -->|受付済み| F["終端回収を待つ"]
    E -->|空き| G["先頭1件を投入"]
    B -->|なし| H{"通常イベントが受付済みか"}
    H -->|受付済み| F
    H -->|なし| I["周期フレームを処理"]
</pre>

F446は両バスでbxCANの送信FIFO優先を無効にしています。通常イベントは1件ずつ終端を待ち、後続の小さいIDのフレームによる追い越しを防ぎます。通常イベントが到着した時点ですでにハードウェアに受け付けられた周期フレームはそのまま終端を待ちます。送信失敗は `CanRouter` が元のトークンで通知し、通常FIFO内での自動再試行はありません。模擬試験は各バス2件の固定領域を使いました。実機で使う容量は未決定です。

## 停止要求の優先送信

`CanTxScheduler::enqueueStop(target, frame, token)` は1バスに最大4対象の停止要求を保存します。対象番号とフレームは要求元が決めます。RS06の4軸、CAN2のC620ゼロ電流とF303停止を独立した対象として扱える構成です。通常FIFOが満杯でも登録でき、未受付の周期指令は登録時に破棄します。停止中に渡された周期指令もフレームは保存せず、世代番号だけ進めます。停止完了後は新しい世代の周期指令を受け付けます。

<pre class="mermaid">
sequenceDiagram
    participant S as 要求元
    participant T as CanTxScheduler
    participant P as CanPort
    participant R as CanRouter
    S->>T: 対象別に停止を登録
    T->>P: serviceで空きメールボックスへ投入
    P-->>R: バス・トークン・送信結果
    R->>T: 対応する送信終端を照合
    alt 送信成功
        T->>T: この対象の停止枠を解放
    else 送信失敗
        T->>T: この対象を再試行待ちに移す
        R-->>S: 失敗を通知
        S->>T: 同じ対象を新しいトークンで再登録
    end
</pre>

未受付の停止はポート未起動やメールボックスの満杯、bus-offでも保持します。別の対象が終端待ち・再試行待ちでも、空きメールボックスを後続の停止に使えます。通常FIFOと直送は全対象の停止送信が成功するまで保留します。通常FIFOは元の順序と期限を保ち、再開時点で期限切れの要求を返します。受付済みフレームは元のトークンで終端まで追跡します。

ここで確認する優先順位は、主ループでメールボックスに入れる順序です。`CanPort` にすでに受け付けられたフレームの送信順序や、物理的な停止は実機側で別途確認します。

## RS06停止・有効化を模擬CAN1へ接続

`MotorCanLink` は `MotorService::pendingRs06Requests()` と `CanTxScheduler` の間で、フレームとトークンを変換します。Type 3の有効化は現周期に `trySubmit()` で受付を試し、受付できなければ次周期に状態から候補を取り直します。通常FIFOに入れないため、DISARM前のType 3が停止後に残りません。すでに受付済みのType 3については、既存の軸状態が終端を待つ間に、他の軸のType 4を先に進めます。

<pre class="mermaid">
sequenceDiagram
    participant A as 制御周期
    participant L as MotorCanLink
    participant S as CanTxScheduler
    participant R as CanRouter
    participant M as MotorService
    A->>R: pollCanEventsで前周期までのイベントを回収
    R->>L: バスとトークンを照合した終端を配送
    L->>M: 終端を該当軸へ反映
    A->>M: RobotSequenceの今回の指令を反映
    A->>L: submitPending
    L->>M: 4軸の候補を取得
    L->>S: Type 4を軸別停止枠へ登録
    A->>S: serviceでメールボックスへ投入
    S-->>A: 投入結果
    A->>L: onScheduledTxProgress
    L->>M: 実際に投入できた軸だけに受付を通知
</pre>

停止枠に登録した時点ではシリアルを1軸1件だけ保存し、枠が空くまで同じ要求を再登録しません。送信終端はCAN1・RS06用の発行元タグ・モータID・シリアルで照合します。送信エラーは故障として通知し、仲裁負けや未送信は再試行可能として返します。いずれも再試行時に軸が新しいシリアルを発行します。CAN1の受信欠落は次の制御周期まで異常をラッチします。

| 統合試験で確認する境界 | 観測結果 |
| --- | --- |
| 3メールボックスと4軸 | 4軸目を専用枠に保持。終端回収後の空き枠から残りを送信 |
| ARMと状態報告 | 同時刻の報告と別バスの報告を除外。4軸すべての送信後のType 2でARM成立 |
| 有効化中のDISARM | 未受付のType 3を破棄。受付済みの軸の停止だけを終端まで待たせる |
| 停止失敗と競合 | 新シリアルで再試行。旧終端と別バス・別発行元の同値シリアルを除外 |
| CAN異常 | bus-offから復旧しても軸別の停止待ちを保持。CAN1のRX欠落を次周期に通知 |

接続の検証基準はPR #41の `818e77b` と、このPRのソース差分です。ホストの通常・UBSanとCTest Debug 17/17、CTest ReleaseのCANイベント回収・送信調停が合格しました。CubeIDE 1.19.0のDebug／Releaseはともにエラー・警告0件で、両構成の22ソースとARM ELF32を確認しました。

この接続の起動と制御周期はホスト試験のフィクスチャで構成しています。基板上でCAN1を起動するコードへの接続、CAN2モータ送信、実CAN・駆動試験は後続です。

## 6軸のフィードバックを1周期分取得

<pre class="mermaid">
flowchart TB
    LEG["CAN1：脚4軸のType 2・24"] --> ROUTER["CANイベント回収と分類"]
    WHEEL["CAN2：左右車輪の0x201・0x202"] --> ROUTER
    ROUTER --> LINK["MotorCanLink：採取時刻付きで配送"]
    LINK --> AXES["MotorService：軸ごとの最新値を保持"]
    AXES --> CYCLE["MotorFeedbackSnapshot：1周期時刻で全軸を評価"]
</pre>

主ループは両バスのイベントを回収してから `MotorService::feedback(nowUs)` を呼びます。RS06の角度・速度・トルク・温度と、C620のロータ角生値・RPM・電流生値・温度を既存のC11デコーダで復号します。左右と軸の順序はAPIで固定し、設定された主機ID・軸IDと一致するRS06報告のみ該当軸に保持します。

スナップショットには周期の評価時刻と、各軸の受信時刻が入ります。未受信の軸は空で、期限が切れた軸は最終値と時刻を保持したまま `fresh == false` を返します。受信時刻からRS06では30 ms、C620では20 msで期限切れになります。RS06のARMと停止の確認に使うType 2の状態・時刻はType 24を受けても維持します。

停止要求は登録時にフレームとトークンを検証します。停止枠からはメールボックスに受付できたときだけ軸へ進捗を返します。実際のCAN送信失敗では既存の終端経路で軸に結果を通知し、停止枠を再試行待ちにします。

| 模擬CANで確認したケース | 結果 |
| --- | --- |
| 受信前と、両バスから6軸分を回収した周期 | 受信前は空。回収後は各軸に正しい値と受信時刻があり、評価時刻は1つ |
| 別バスの報告、RS06の主機違い・予約モード、C620の対象外ID・範囲外ロータ角 | 既存値と鮮度を更新しない |
| 期限の直前とちょうど、次周期にスナップショットを取得 | 直前は新鮮。ちょうどで期限切れ。取得済みの前周期コピーは変化しない |
| ARMからDISARM、停止失敗・bus-offから復旧 | 既存のCAN1試験と停止再試行の回帰に合格 |

ソース・テストの検証基準は `8eb9f42` からの差分です。 `python3 tools/run_host_tests.py` の通常とUBSan、CTest Debug 17/17、CTest ReleaseのCANイベント回収1/1が合格しました。CubeIDE 1.19.0のDebug／Releaseともにエラー・警告0件で、全AppソースのコンパイルとARM ELFを確認しました。仕様リンク・CubeIDE設定監査も合格しました。Doxygen 1.9.8でHTMLを生成し、新規・改名ファイルの一覧リンクと両ページのMermaidブロックを確認しました。実機CANでの受信、物理換算値の照合、実機駆動は未検証です。

## 確認した範囲

| ケース | 確認項目 |
| --- | --- |
| 両バスにイベントが滞留 | CAN1の受信キューが空く前にCAN2のbus-offと送信終端を配送する。同値トークンがバス・時刻と組のまま届く |
| 配送のたびにIRQで補充 | ポートごとの上限で戻る。上限で残ったイベントは次回配送する |
| 受信先の判定 | 両ポートの受信キューからRS06とC620左右を配送する。バス違い、標準・拡張違い、短いDLC、範囲外ID、電流指令と未確定IDは未分類になる |
| CAN1/CAN2で同じトークンを各3件受付 | CAN2のエラー終端はCAN2だけを解放。CAN1が4件目を投入できるのはCAN1の終端を回収した後 |
| 受付状態と終端の照合 | `Busy`・`Invalid`・`NotReady` 後、発行元不一致、時刻逆行、重複を棄却。同時刻の正当な終端と、全4種の終端結果を配送 |
| CAN1の4番目の周期送信 | 同じ世代では最初に空いた枠を使用。次の世代が来た場合は新データだけを旧世代の終端回収後に投入 |
| 周期の期限と一括更新 | 期限直前は受付可能、期限ちょうどで破棄。無効フレーム・重複トークン・古い再登録で旧世代の待ちを書き換えない |
| CAN2のC620共通フレーム | CAN1の終端と独立に、模擬CAN2の旧送信終端後に左右のペイロードを1件で更新 |
| 通常イベントと周期フレームが同時に待機 | 通常イベントの受付順を維持し、最後の終端を回収してから周期フレームを投入。別バスの終端では待ちを解除しない |
| 通常FIFOの満杯・期限切れ | 満杯で既存データを保持。ポート起動前・満杯でも期限切れを通知。解放した領域を順序を保ったまま再利用 |
| 停止を4対象、通常FIFOを満杯にする | 4対象すべてを別枠で登録し、3メールボックスの空きから先に投入。最後の停止成功後に通常FIFOを元の順で再開し、停止前・停止中の周期指令を復活させない |
| 停止送信が終端で失敗 | 仲裁負け、送信エラー、未送信で停止枠を維持。同じトークンの再登録、別バスの同値トークン、古い終端による誤解除を防止 |
| 停止登録後にポート未起動・bus-off | 受付できるまで保持し、復旧後に投入。再試行待ちの対象がいても他の停止対象を処理する |
| CAN1のみ・CAN2のみ・両方未接続 | 利用できるポートだけを回収する。CAN1監視は既存の受信件数とバス状態を維持する |

停止送信の検証基準は `master` の `4cbecc8` と、このPRのソース差分です。

| 検証 | 結果 |
| --- | --- |
| `python3 tools/run_host_tests.py` | 通常・UBSanとも合格 |
| CMake／CTest | Debug 17/17合格。ReleaseのCANイベント回収・送信調停の試験1/1合格 |
